한눈에 보는 발견
  • (10-22 추가) 기능 폭은 이제 6곳 중 가장 넓은 축에 든다. 매트릭스 29행 중 Artipin이 지원하는 것은 19행, 일부 지원이 2행이다. 다만 Artipin 열은 코드로 확인한 값이고 경쟁사 열은 페이지에 적힌 것만 센 값이라, 이 비교는 Artipin 쪽에 유리하게 기운다. 남은 빈칸은 대부분 'AI 루프' 묶음(내보내기, MCP·CLI, AI가 댓글 읽고 수정, 이슈 트래커)이다. 루프의 앞단(댓글 수집)과 뒷단(같은 링크 교체·버전)은 갖췄고, 그 둘을 잇는 가운데(피드백을 AI에 넘기는 단계)가 비어 있다. 아래 10-19 발견 중 '루프의 앞단만 갖고 있다'는 항목과 '범위 폭주' 항목은 이 변화를 감안해 읽는다.
  • 핵심 웨지는 이미 시장의 최소선이다. '링크 + 로그인 없는 핀 댓글 + 격리 샌드박스'는 coeditHTML·commentable·Tiiny 모두 갖고 있다. 이것만으로는 차별이 되지 않는다(설계서가 인용한 사업성 평가 '차별성 3/10'과 같은 결론).
  • 시장은 '댓글 → AI 수정 → 같은 링크 갱신' 루프로 수렴 중이다. 6곳 중 5곳이 AI 연동(MCP·CLI)이나 내보내기를 갖고 있고, 4곳이 같은 링크로 새 버전을 올린다. Artipin은 이 루프의 앞단(댓글 수집)만 갖고 있다.
  • Artipin에게 남는 차이는 두 가지다. ① 댓글에 로그인이 필요한 곳(HaveTML)이 있는 반면 Artipin은 없다. ② 6곳은 모두 외부 호스팅형이다. 사내 서버에 설치해 데이터를 밖으로 내보내지 않는 점은 이 조사에서 직접 대응하는 제품을 찾지 못했다(coeditHTML이 소스를 공개했다고 하나 자체 호스팅 가능 여부는 확인하지 못함). 이 둘째 항목은 조사 결과에서 끌어낸 추론이고 수요 검증은 아직 없다.
  • 기능이 많은 곳(BugSmash·HaveTML)은 그대로 따라가면 범위가 폭주한다. 그래서 이 문서는 '많이 가진 곳이 있는가'가 아니라 '웨지를 끝까지 닫는 데 필요한가'로 판정한다.
읽기 전에 — 이 조사의 한계
  • 정보는 2026-10-19에 각 페이지 본문을 가져와 요약한 것이다. 페이지에 적힌 문구만 근거로 삼았고, 실제로 가입·사용해 보지는 않았다. 10-22 갱신은 Artipin 쪽(커밋·코드)만 다시 확인했고 경쟁 서비스는 다시 조사하지 않았다.
  • 매트릭스의 –는 '페이지에 언급 없음'이지 '없다'는 뜻이 아니다. 가격표는 대부분 확인하지 못했고(HaveTML은 /pricing 미열람), BugSmash 가격은 구조화 데이터 기준이다.
  • 확인된 사용자 수요는 아직 없다. 설계서의 수요 근거는 '가설 단계'다. 그래서 '추천'도 '사용자가 요구했다'가 아니라 '다음에 만든다면 비용 대비 근거가 가장 크다'는 뜻이고, 나머지는 모두 착수 조건을 두었다(불필요한 선제 구현을 피하는 프로젝트 원칙에 따른다).

3벤치마킹 대상 6곳

coeditHTML

https://coedithtml.com

독립형 HTML을 링크로 공유하고, 실행된 상태 그대로 검토·편집한다.

  • 보기·댓글·편집 3단계 권한을 링크별로 발급하고 개별 취소
  • 텍스트 드래그 댓글 + 차트·이미지 위 스티커 메모, 사이드바에 피드백 모아보기
  • 본문 텍스트 직접 수정(되돌리기 가능), 원본 파일은 불변 보관
  • 피드백을 마크다운으로 복사, 변경 반영된 HTML 다운로드
  • 격리 도메인 샌드박스, 선택적 비밀번호, 계정 불필요(이름만 입력)
  • HTML 5MB, 다중 파일·빌드 필요 프로젝트 미지원, 소스 GitHub 공개

가격·한도 개인 무료(카드·계정 불필요). 기업 도입은 별도 문의. 5MB 외 한도는 페이지에 없음.

Artipin에 주는 시사점 구조·한도·보안 모델이 Artipin과 가장 닮았다. 차이는 '편집 권한'과 '마크다운 내보내기'. 따라 할 가치가 있는 것은 후자다.

HaveTML

https://havetml.com

AI 도구에서 바로 게시하는 아티팩트 호스팅 + 캔버스·실시간 협업·E2EE까지 가진 가장 넓은 제품.

  • HTML·Markdown·YAML·JSON 지원, 영구 링크, 비공개 → 링크 공유 → 공개 3단계
  • 같은 링크 뒤에서 새 버전 업로드
  • 실시간 접속자·커서·즉시 갱신 댓글(협업자 초대는 Pro)
  • 공유 JSON 상태 + 서명된 웹훅으로 에이전트가 페이지 변화를 감시
  • 브라우저 AES-256 암호화(키는 URL # 뒤라 서버로 안 감)
  • Claude 원클릭 OAuth, Claude Code·Cursor·Codex는 설정 붙여넣기(MCP, 전 플랜 무료)
  • 캔버스 보드, Explore, Circles(그룹 공유), 하위 폴더, Chrome 확장

가격·한도 무료로 시작(카드 불필요). Pro: 협업자 초대·비밀번호·만료. 가격표(/pricing)는 열람하지 못함.

Artipin에 주는 시사점 댓글을 달려면 가입해야 한다. Artipin의 '로그인 없는 댓글'이 분명한 차이다. 범위가 넓어 그대로 따라가면 안 되는 대표 사례.

Artifact Share

https://artifactshare.com

AI가 올리고, 사람이 댓글을 달면 AI가 읽고 고쳐 같은 URL로 갱신하는 루프.

  • Claude Code·Codex·Cursor용 CLI, 채팅 AI용 MCP 서버(artifactshare.com/mcp)
  • 같은 URL로 업데이트, 전체 버전 기록
  • 위치 지정 댓글 → AI가 댓글을 읽고 수정한 뒤 답글
  • 기본은 워크스페이스 내부 공개, 외부는 만료 링크·일회용 이메일 코드
  • 회의록 정리, 인터랙티브 UI 목업 검토 등 사용 사례 제시

가격·한도 무료 100MB, 사용자 수 무제한, 인원과 무관한 정액제. 유료 플랜 가격은 페이지에 없음.

Artipin에 주는 시사점 시장이 '댓글 → AI 수정 → 같은 링크 갱신'으로 수렴하고 있음을 보여주는 가장 명확한 증거. Artipin이 이 루프의 앞단(댓글 수집)을 이미 갖고 있다.

commentable.link

https://www.commentable.link

HTML·PDF 위에 핀 댓글만 남기는 최소 기능 제품. E2EE가 중심 메시지.

  • HTML 붙여넣기 → 렌더링 → 요소 클릭 핀 댓글, 공유 전 라이브 미리보기
  • PDF는 페이지별 위치 고정 댓글, 리더 불필요
  • 댓글 해결·재개 버튼, 피드백을 AI용으로 내보내기
  • AES-256-GCM 브라우저 암호화, 키는 링크에만, null-origin 샌드박스, noindex·robots 차단
  • 계정 없이 댓글, 역할별 권한은 없음

가격·한도 두 도구 모두 무료(카드 불필요). 유료·한도 정보 없음.

Artipin에 주는 시사점 웨지가 Artipin과 거의 같다(링크 + 핀 + 해결). 새로 배울 것은 '내보내기'와 noindex 정도로, 이 사이트가 최소 제품의 상한선에 가깝다.

Tiiny Host · Feedback Mode

https://tiiny.host/feature/feedback-mode/

정적 호스팅 서비스에 붙은 부가 기능. 100종 이상 파일에 핀 주석을 단다.

  • 프레젠테이션·PDF·HTML 등 100종 이상, 계정 없이 핀 주석
  • 원클릭 비밀번호(링크와 별도 공유)
  • 검토 중에도 파일 교체·브라우저 편집, 링크 유지, 이전 버전 보관과 롤백
  • 팀 협업은 Pro
  • TLS 암호화 전송

가격·한도 무료로 시작, Pro에서 팀 협업. 세부 한도는 페이지에 없음. 알림·해결 처리·답글은 페이지에 언급 없음.

Artipin에 주는 시사점 '검토 중에 파일을 바꿔도 링크가 안 바뀐다'가 기본 전제다. 비동기 검토(리뷰어가 동시에 접속하지 않음)를 명시한 점도 Artipin의 사용 방식과 맞다.

BugSmash

https://bugsmash.io/html-feedback/

에이전시·QA 지향의 무거운 제품. 피드백을 작업(task)으로 바꾸는 데까지 간다.

  • 핀 댓글, 스레드·답글, 해결, 작업 전환(지정·우선순위)
  • 데스크톱·태블릿·모바일 뷰포트 전환, 댓글에 브라우저·기기 정보 첨부
  • 새 빌드 업로드 시 버전 비교, 피드백은 새 버전에도 유지
  • .html 또는 CSS·JS·이미지·폰트를 담은 .zip(페이지 50MB, 로그인 시 100MB)
  • AI 리뷰어(접근성·UI/UX·맞춤법·깨진 링크)와 고객별 커스텀 리뷰어, MCP로 에이전트가 댓글 읽고 수정본 업로드
  • Jira·Linear·Trello 내보내기, Public·Private·Password 프로젝트, 워크스페이스 기본값, Agency 화이트라벨·자체 도메인

가격·한도 Free(첫 프로젝트 체험용으로 보임 — 표기가 'Free forever'와 엇갈림), Starter $19, Team $49, Agency $99. 플랜별 한도는 페이지에 없음.

Artipin에 주는 시사점 기능은 가장 많지만 사내 MVP에는 대부분 과하다. 가져올 것은 뷰포트 전환 같은 '작은 것'뿐이고, 나머지는 범위 폭주의 경고로 읽는다.

5기능별 판단: 추천 / 적용 보류

P1

피드백 마크다운 내보내기

추천

벤치마크 근거 coeditHTML · commentable (AI 루프 계열: Artifact Share · BugSmash · HaveTML)

무엇 소유자가 한 번의 클릭으로 파일의 댓글을 마크다운으로 복사한다. 항목마다 작성자, 본문, 해결 여부, 앵커(CSS 선택자 또는 이미지 좌표), 답글을 담는다. 미해결만 복사하는 선택지를 둔다.

추천 이유 Artipin의 사용자는 AI 산출물을 만든 사람이고, 피드백의 다음 행선지는 거의 확실히 '그 AI에게 다시 붙여넣기'다. 지금은 패널을 눈으로 읽고 손으로 옮겨 적어야 하고, 이 구간이 '링크 + 핀 댓글' 웨지의 마지막 한 칸이다. 6개 사이트 중 5곳이 이 루프(내보내기 또는 에이전트 연동)를 제공해 벤치마크 신호가 가장 강하다. 반면 구현은 가장 작다. 외부 서비스·토큰·스키마 변경이 필요 없다.

Artipin 적용 범위 뷰어의 댓글 패널이 이미 댓글 목록과 앵커를 받아 쓰므로, 새 API 없이 클라이언트에서 문자열을 조립해 클립보드에 복사하는 방식이 가능해 보인다(착수 시 CommentItem에 앵커가 들어 있는지 확인). 소유자 세션에서만 버튼을 노출한다.

주의 선택자만으로는 AI가 요소를 못 찾을 수 있다. 첫 사용 후 '요소 텍스트 앞 40자' 같은 문맥이 필요하다고 확인되면 그때 앵커에 추가한다(미리 넣지 않는다). 방문자 이름이 그대로 복사되므로 외부 채널에 붙여넣을 때 유의.

10-22 현황 아직 구현되지 않았다(현재 클립보드 복사는 공유·초대·암호화 링크 복사뿐). 그사이 앵커가 늘어서 범위를 다시 잡아야 한다. 내보내기 항목에 드래그 댓글의 인용문(quote)과 PDF 쪽 번호(page)를 함께 담는다. 인용문은 위 '주의'의 '선택자만으로는 요소를 못 찾는다'는 문제를 일부 덜어 준다. 버튼은 소유자 세션이 아니라 관리 권한(canManage, 팀 멤버 포함)으로 노출한다. 보기 전용 뷰어에는 댓글이 없으니 해당 없다. E2EE 파일도 인용문·선택자는 평문으로 저장되므로 내보낼 수 있다.

P2

같은 링크로 새 버전 교체(덮어쓰기)

구현됨 · 10-2110-19 판정: 추천

벤치마크 근거 Tiiny · HaveTML · Artifact Share · BugSmash

무엇 소유자가 기존 파일을 새 파일로 교체한다. 공유 토큰·댓글·조회 기록은 유지하고 본문만 바뀐다. 버전 목록·비교·롤백은 만들지 않는다.

추천 이유 AI 산출물은 '댓글 → 재생성 → 다시 공유'가 기본 동작이다. 지금은 새로 올리면 새 링크가 되어 받는 사람이 링크를 다시 받고, 이전 댓글 맥락이 끊긴다. 6개 중 4곳이 '링크 유지'를 기본으로 제공한다는 건 이 불편이 일반적이라는 뜻이다. 설계 문서의 지표 (c) '같은 사람이 다시 올렸는가'도 사실상 이 행동을 측정한다. 교체 기능이 있으면 재업로드가 신규 파일이 아니라 같은 파일의 갱신이 되어 지표 정의를 함께 손봐야 한다는 점은 알아 둘 것.

Artipin 적용 범위 파일 교체 Route Handler 1개(소유자 세션 + 형식·한도 검사는 기존 upload.ts 재사용), 저장 파일 덮어쓰기, /api/files 목록의 교체 버튼. 콘텐츠 응답의 캐시 헤더가 교체 직후에도 새 본문을 내보내는지 확인 필요.

주의 교체 후 선택자가 맞지 않는 핀은 설계상 '핀 없이 목록에만' 표시되므로 최악의 경우에도 댓글은 남는다. 다만 '이미 반영된 지적'과 '새 콘텐츠에 대한 지적'이 섞여 헷갈릴 수 있으니, 필요해지면 그때 소유자가 해결 처리로 정리하게 한다(별도 버전 표시는 만들지 않음). 이전 본문은 복구할 수 없다는 점을 확인 문구로 알린다.

구현 결과 f5c550b·48d2867 (#27·#28) PUT /api/files/[id]로 같은 종류의 파일로만 교체하고, 토큰·댓글·조회 기록은 유지한다. /c/* 응답에 Cache-Control: no-cache를 붙였고, 지표 (c)는 교체한 소유자도 세도록 정의를 바꿨다. 이 항목은 '버전 목록·비교·롤백은 만들지 않는다'고 했지만 바로 다음 커밋에서 file_versions 테이블에 모든 본문을 남기고 이전 버전 보기·나란히 비교·롤백까지 만들었다. 그래서 '이전 본문은 복구할 수 없다'는 주의는 더 이상 맞지 않고, 교체 확인 문구도 되돌릴 수 있다는 내용으로 바뀌었다.

W1

AI 에이전트 연동(개인 API 토큰 → MCP/CLI)

적용 보류 · 트리거 대기

벤치마크 근거 HaveTML · Artifact Share · BugSmash (coeditHTML은 메뉴만 확인)

무엇 AI 도구가 직접 파일을 올리고 댓글을 읽게 한다. 단계는 ① 소유자별 API 토큰으로 업로드·댓글 조회 API 호출 ② 그 위에 MCP 서버.

보류 이유 시장 방향은 분명하지만 지금 만들 이유가 없다. 설계 문서가 CLI/MCP를 MVP에서 제외했고, 사용 사례가 불명확하다. 인증 모델(세션 쿠키 → 토큰), 토큰 폐기, 에이전트가 만드는 대량 업로드 처리까지 한 번에 따라온다. 또한 P1(내보내기)을 먼저 쓰면 '복사·붙여넣기가 병목인가'가 데이터로 드러나, 이 항목의 필요성을 싸게 검증할 수 있다.

착수 트리거 P1 내보내기를 쓰는 소유자가 매번 같은 파일을 AI에 되먹이는데 복사가 번거롭다는 관찰, 또는 업로드를 사람 손이 아니라 AI 세션에서 직접 하고 싶다는 요청.

W2

뷰포트 전환 + 댓글에 뷰포트·브라우저 정보 첨부

구현됨 · 10-2110-19 판정: 트리거 대기

벤치마크 근거 BugSmash

무엇 뷰어에서 iframe 폭을 데스크톱·태블릿·모바일로 전환하고, 댓글 저장 시 당시 뷰포트와 UA를 같이 남긴다.

보류 이유 구현은 작지만(iframe 폭 토글) 수요 증거가 BugSmash 한 곳뿐이다. '모바일에서는 깨져요' 같은 지적이 댓글로 반복돼야 가치가 확인된다. 핀 앵커는 요소 선택자 + 요소 내 상대좌표라 폭이 달라도 대체로 유지되지만, 폭에 따라 레이아웃이 달라지면 같은 핀이 다른 곳에 보일 수 있다.

착수 트리거 반응형·모바일 관련 댓글이 2주 관찰 중 반복되거나, 소유자가 모바일 확인용으로 별도 캡처를 보내는 사례.

구현 결과 4d95c98 (#30) 뷰어 툴바에서 데스크톱(100%)·태블릿(768px)·모바일(390px)로 전환하고, 핀 박스 기준 영역도 함께 좁아진다. 선택한 폭은 저장하지 않는다. 앞의 절반만 구현했다. 댓글에 뷰포트·브라우저 정보를 남기는 부분은 없고, 그 부분은 원래 트리거(반응형 지적 반복)를 그대로 따른다.

W3

Markdown(.md) 업로드

구현됨 · 10-2110-19 판정: 트리거 대기

벤치마크 근거 HaveTML · Artifact Share

무엇 마크다운 파일을 올리면 서버가 HTML로 변환해 기존 HTML 흐름으로 서빙한다.

착수 트리거 '.md를 HTML로 바꿔서 다시 올렸다'는 사례, 또는 업로드 거절(확장자 오류) 기록이 반복될 때.

종단간 암호화(E2EE)

구현됨 · 10-2210-19 판정: 방향 불일치

벤치마크 근거 HaveTML · commentable.link

무엇 브라우저에서 암호화하고 키를 URL 해시에만 두어 서버가 내용을 못 읽게 한다.

보류 이유 Artipin의 구조와 정면으로 충돌한다. 서버가 HTML에 브리지를 주입하고 CSP 헤더를 붙여 서빙하는 구조인데, E2EE에서는 복호화가 브라우저 안에서만 일어나 서버 주입이 불가능하다. 사내 서버를 신뢰하는 배포에서는 얻는 이득도 작다. 링크를 잃으면 복구할 수 없다는 비용도 사내 도구에 맞지 않는다.

구현 결과 0a917f7 (#41) 브라우저가 형식을 판정한 뒤 AES-GCM-256으로 암호화해 암호문만 올리고, 키는 /s/{token}#k=… 프래그먼트에만 둔다. 이 항목이 '서버가 브리지를 주입할 수 없다'고 본 충돌은 콘텐츠 호스트의 봉투 문서(같은 CSP sandbox)에 복호화한 평문을 넘기고 그 안에서 브리지를 넣는 방식으로 피했다. 대신 HTML·이미지만 지원하고(PDF·zip·Markdown·JSON 거절), 교체·버전·편집·보기 전용·재발급은 막힌다. 키를 잃으면 복구할 수 없다는 비용은 그대로다. 악의적 서버, 문서 자신의 외부 전송, 제목·인용문·선택자 평문 저장은 막지 못한다고 위협 모델 문서에 적었다.

S2

본문 직접 편집

구현됨 · 10-2210-19 판정: 방향 불일치

벤치마크 근거 coeditHTML · Tiiny

무엇 검토자나 소유자가 페이지 안에서 텍스트를 직접 고치고 수정본을 다운로드한다.

보류 이유 Artipin의 가치는 '원본은 AI가 만들고, 사람은 의견만 남긴다'는 분리다. 편집을 넣으면 어느 쪽이 원본인지 모호해지고, 편집 결과를 반영하려면 샌드박스 안에서 DOM을 쓰고 저장하는 새 경로가 필요하다. AI에게 수정 지시를 하는 편이 빠르다.

구현 결과 dc61ac7 (#40) 반대했던 형태와 다른 좁은 형태로 들어갔다. 소유자만, 단일 HTML에서, 텍스트만 가진 요소를 고칠 수 있다. 서버 원본은 바꾸지 않고 수정본 HTML을 내려받아 교체로 반영한다. 원본은 여전히 서버의 버전 하나라서 이 항목이 걱정한 '어느 쪽이 원본인가' 문제는 생기지 않는다. 검토자 편집은 없다.

S3

동적 JSON 상태 · 웹훅

적용 보류 · 방향 불일치

벤치마크 근거 HaveTML

무엇 페이지가 공유 JSON 상태를 유지하고 에이전트가 변경을 구독한다.

보류 이유 Artipin은 콘텐츠에 connect-src 'none'을 걸어 업로드 HTML이 어디에도 요청을 못 보내게 하는 것이 보안 전제다. 이 기능은 그 전제를 반대로 푸는 것이고, 제품 정체성도 '검토 도구'에서 '앱 호스팅'으로 옮긴다.

S4

실시간 협업(접속자·커서) · 자동 갱신

구현됨 · 10-2210-19 판정: 방향 불일치

벤치마크 근거 HaveTML

무엇 다른 사람의 커서와 새 댓글이 새로고침 없이 반영된다.

보류 이유 설계서가 실시간 갱신을 제외했다. 단일 컨테이너 + SQLite에서 WebSocket·SSE를 유지하는 부담이 있고, 사용 방식(비동기 검토)과 맞지 않는다. 동시에 모여 검토하는 회의가 실제로 생기면 그때 폴링부터 검토한다.

구현 결과 5279b05·d40140e (#39) 이 항목이 말한 대로 폴링부터 시작했다. 댓글은 보이는 탭에서 15초마다 폴링하고, 접속자 수는 폴링 heartbeat로 서버 메모리에서 센다(2명 이상일 때만 표시). 커서만 SSE로 중계한다. 단일 인스턴스 메모리 상태가 전제라 인스턴스를 늘리면 다시 설계해야 한다. 업로드 HTML에 다른 방문자의 위치·활동 시점이 노출된다는 점을 구현 전에 위협 모델 문서에 먼저 적었다.

S5

AI 자동 리뷰어(접근성·UI/UX·맞춤법·깨진 링크)

적용 보류 · 방향 불일치

벤치마크 근거 BugSmash

무엇 업로드 시 AI가 자동으로 점검하고 결과를 댓글로 남긴다.

보류 이유 사람의 피드백을 받는 도구에 AI 평가를 섞으면 제품이 둘로 갈라진다. 모델 호출 비용·키 관리·결과 품질 책임이 생기고, 같은 일은 소유자가 AI 도구에 직접 시키면 된다.

적용 보류 · 방향 불일치

벤치마크 근거 HaveTML · Artifact Share · BugSmash

무엇 보드, 공개 탐색, 그룹 공유, 중첩 폴더, 회의록 정리, 고객사 브랜딩 포털.

보류 이유 문서 허브·에이전시 제품으로 가는 방향의 기능들이다. 웨지('링크 하나 + 핀 댓글')를 흐리고 사내 MVP의 검증 지표(전달·댓글·재업로드)와도 무관하다. 파일이 많아져 목록 정리가 필요해지면 폴더가 아니라 정렬·검색 같은 작은 도구부터 본다.

6권장 순서와 보류 항목 재검토 방법

10-19의 원래 순서는 ① P1 내보내기 ② P2 교체(P1과 병행) ③ 2주 관찰 후 트리거 점검이었다. P2는 끝났고 P1은 남았다. 아래는 10-22에 다시 쓴 순서다.

P1 피드백 마크다운 내보내기 — 여전히 가장 작고 근거가 크다. 이제는 교체·버전이 있어서 '내보내기 → AI 수정 → 같은 링크로 교체' 루프를 Artipin 안에서 끝까지 돌 수 있다. 인용문·PDF 쪽 번호를 함께 담는다(5절 P1의 10-22 현황 참조).
W6 noindex 헤더 — 비용은 헤더 한 줄이다. 배포 호스트가 외부에서 도달 가능한지만 확인하고, 그렇다면 P1과 상관없이 넣는다.
사용 관찰과 트리거 점검 — 사흘 사이 기능이 12가지 늘었으므로, 무엇을 더 만들기 전에 늘어난 기능이 실제로 쓰이는지 먼저 본다(설계서 지표: 전달·댓글·재업로드). 그다음 아래 표로 남은 보류 항목을 점검하고, 조건이 확인된 것만 이슈로 만든다.
보류 항목무엇을 보고 판단하는가
W1 AI 연동P1 내보내기 사용 빈도, 복사·붙여넣기가 번거롭다는 발언
W2 남은 절반(기기 정보 첨부)뷰포트 전환을 쓴 뒤에도 '어느 기기에서 봤는지'를 댓글로 되묻는 사례
W6 noindex배포 호스트의 외부 도달 가능 여부(W4가 구현됐으므로 사실상 확인만 남음)
W8 이슈 트래커P1 결과를 이슈로 옮겨 적는 일이 반복되는지

10-19 표에 있던 W3·W4·W5·W7·W9·W10·W11은 구현돼 표에서 뺐다. 원래 판단 기준은 5절 각 항목의 '착수 트리거'에 남아 있다.
