## Problem Statement

AI로 만든 HTML·이미지 산출물을 다른 사람에게 보여주고 피드백을 받을 때, 지금은 캡처를 메신저로 보내고 말로 피드백을 받는다. 해결 단위는 "링크 하나 + 화면 위치 핀 댓글"이다. 사내 프로젝트로 빠르게 만들어 필요 기능을 확정한 뒤 스타트업·사업화로 전환한다.

출발점은 ChatGPT 사업성 평가(공유 링크 `chatgpt.com/s/t_6ad1c8b629bc81918e910e5e327cb620`)다. 평가의 핵심: 시장 차별성 3/10, 유료 전환 5/10, 경쟁 제품(coeditHTML, HaveTML, Artifact Share, commentable.link, Tiiny Host, BugSmash)이 이미 같은 기능을 제공한다. 경쟁 정보는 리포트 기준이며 이 세션에서 검증하지 않았다.

## Demand Evidence

- 증거 수준: **가설 단계.** 본인의 불편에서 출발했고(D1: "내 불편에서 출발, 타인은 미확인") 공유받는 쪽의 반응은 확인하지 않았다.
- 현재 대안(D2): 캡처를 메신저로 보내고 말로 피드백 받기. 소요 시간·빈도의 숫자는 아직 없다.
- 이 약점은 첫 이슈(#1)에서 직접 다룬다.

## Status Quo

캡처 → 메신저 → 텍스트로 "그림 오른쪽 위 차트 색을 바꿔주세요" 식 설명. 위치를 말로 지정해야 하고, 인터랙티브 HTML은 캡처하면 상호작용이 사라진다.

## Target User & Narrowest Wedge

- 소유자(올리는 사람): 본인(AI 산출물 제작자).
- 댓글 작성자(D3): "개발자, 기획자, 고객, 경영진" — 직군 단위이며 **이름 있는 사람은 아직 없다.**
- 웨지: 파일 업로드 → 링크 복사 → 로그인 없이 화면 위치 핀 댓글 → 소유자가 확인·해결 처리. 이 흐름이 끝까지 한 번 동작하는 것이 최소 단위다.

## Constraints

- Next.js 최신 안정 버전, Biome(lint/formatter), pnpm 필수.
- 구현 계획은 GitHub 이슈로 등록해 진행. 참고 문서는 self-contained HTML로 `docs/`에 저장.
- 각 단계에서 과도한 테스트와 확인된 요구 없는 선제적 복잡도 금지.
- 배포: 사내 컨테이너·서버(영속 볼륨, 호스트명 2개 확보 가능 — D7 응답).

## Premises

1. 해결할 문제는 "캡처를 메신저로 보내고 말로 피드백 받는 번거로움"이다. 해결 단위는 "링크 하나 + 화면 위치 핀 댓글".
2. **MVP 입력은 이미지(PNG/JPG/WebP)와 독립형 HTML 둘 다다.** (제안은 "이미지 먼저, HTML 2단계"였으나 사용자가 반대해 HTML 포함으로 확정.) 위험: 현재 대안이 캡처라는 D2 답변과 어긋나므로, 인터랙션 보존이 실제로 필요한지는 이슈 #1의 관찰로 확인한다.
3. 댓글 작성자는 로그인 없이 이름만 입력한다. 소유자만 인증한다.
4. MVP 필수: 업로드, 링크 공유(보기+댓글), 핀 댓글과 답글, 해결/재개, 내 파일 목록·삭제(삭제하면 링크 중단). 제외: 버전·비교, 비밀번호·유효기간, 실시간 갱신, AI 내보내기, CLI/MCP, 팀 관리, 댓글 잠금, 표시/숨김 토글. 요구가 확인될 때 추가한다.
5. Next.js 단일 앱. 별도 백엔드 서버 없이 Route Handlers/Server Actions. (ChatGPT 리포트의 Litestar/Django는 쓰지 않는다.)
6. 사업화 판단 지표 3개를 구현 전에 정한다: (a) 올린 사람이 링크를 실제 전달했는가 (b) 받은 사람이 댓글을 달았는가 (c) 같은 사람이 다시 올렸는가. DB 조회로 확인하고 분석 도구는 넣지 않는다.

## Approaches Considered

- **A. 린 단일 컨테이너 (선택):** Next.js + SQLite(Drizzle) + 로컬 디스크 볼륨, 컨테이너 1개. 사람 ~2주 / CC ~3~4시간.
- B. Postgres + S3 호환 스토리지: 사외 공유·다중 인스턴스가 필요해지면 이전. 지금은 인프라 준비와 로컬 환경 비용이 확인된 요구보다 큼.
- C. B + Cloudflare R2/Worker 콘텐츠 도메인: 남용·대규모 트래픽은 확인되지 않은 요구라 기각.
- (세션 중 기각) 이미지 먼저·HTML 2단계: 사용자가 HTML 포함을 선택.

## Recommended Approach

접근 A. 업그레이드 트리거: 사외 사용자와 공유 시작 또는 다중 인스턴스 필요 → B로 이전.

### 공통 설계

**HTML 안전 실행** (가장 큰 기술 위험)
- 콘텐츠 전용 호스트명(`CONTENT_HOST`)과 앱 호스트명(`APP_HOST`)을 Host 헤더로 분기한다. 같은 컨테이너가 둘 다 처리한다.
- 콘텐츠 응답 헤더(기본 정책): `Content-Security-Policy: sandbox allow-scripts; connect-src 'none'; form-action 'none'; frame-ancestors <APP_HOST>`, `X-Content-Type-Options: nosniff`. `default-src`는 두지 않으므로 외부 스크립트·이미지·스타일(CDN 차트 라이브러리 등)은 **허용**하고 fetch/XHR/폼 전송만 차단한다. Content-Type은 업로드된 값을 믿지 않고 `text/html; charset=utf-8`로 고정한다. 이 기본값을 좁힐지는 실제 AI 생성 HTML 샘플 확인 뒤 정한다(Open Question 5).
- 콘텐츠 URL은 `https://{CONTENT_HOST}/c/{share_token}` 하나다. **이미지와 HTML 모두 CONTENT_HOST에서 서빙**하고 접근 조건은 128비트 토큰뿐이다(추측 가능한 id 경로 없음). 삭제 후에는 두 호스트(`/s/{token}`, `/c/{token}`) 모두 404를 반환한다.
- 호스트별 허용 경로: CONTENT_HOST는 `/c/*`만 응답하고, APP_HOST는 업로드 파일 본문을 직접 서빙하지 않는다. 앱 세션 쿠키는 Domain 속성 없는 호스트 전용 쿠키다.
- 뷰어 페이지: `<iframe sandbox="allow-scripts">` (`allow-same-origin` 금지). 불투명 출처라 앱 쿠키·스토리지에 접근할 수 없다. 알려진 한계: 이 샌드박스에서는 `localStorage`/`document.cookie` 접근이 예외를 던지고 `alert`·폼 제출·새 창 링크가 막혀, 로드 시 localStorage를 쓰는 HTML은 깨질 수 있다. MVP는 이를 한계로 받아들이고(저장소 대체 shim은 넣지 않는다) 샘플 확인 항목에 포함한다.
- 별도 등록 도메인이 아니라 호스트명 분리로 시작한다. 이유: CSP `sandbox` 헤더와 iframe `sandbox`가 이미 불투명 출처를 강제한다. 사외 공유 시작 시 등록 도메인 분리를 다시 검토한다.

**핀 댓글 앵커**
- `anchor`는 `{ kind: "image", x, y }`(이미지 크기 대비 0~1) 또는 `{ kind: "html", selector, relX, relY }`(요소 내 상대좌표 0~1).
- 서빙할 때 HTML에 브리지 스크립트를 주입한다. 브리지가 탐색/댓글 모드 전환, 클릭 시 CSS 선택자·상대좌표 계산, 핀 렌더링을 iframe 안에서 처리하고 `postMessage`로 부모와 통신한다.
- 부모는 `event.source === iframe.contentWindow`로 검증하고, 브리지는 `event.source === window.parent`만 받는다. 메시지 종류는 `mode`, `anchor-picked`, `render-pins` 정도로 최소화한다.
- 브리지는 신뢰할 수 없는 HTML과 같은 문서에서 돌므로 적대적 HTML이 `anchor-picked`를 위조할 수 있다. 부모는 메시지를 신뢰할 수 없는 입력으로 취급해 종류 허용 목록, `relX`/`relY` 0~1 범위, `selector` 문자열 타입·길이 상한(예: 500자)을 검사하고, 값은 항상 텍스트로만 렌더한다(HTML로 해석하지 않음). 위조된 앵커의 최악 결과는 엉뚱한 위치의 핀이다.
- 선택자를 찾지 못한 댓글은 핀 없이 댓글 목록에만 표시한다(별도 복원 로직 없음). 탭·필터 상태 복원은 범위 밖.

**데이터 (SQLite)**
- `owners`(provider, provider_account_id — 둘이 유일, email(표시용·null 가능), name), `files`(owner, kind image|html, title, storage_path, size, share_token, created_at, deleted_at), `comments`(file, parent, author_name, visitor_id, is_owner, body, anchor JSON, resolved_at, created_at), `views`(file, visitor_id, first_seen_at; 복합 PK).
- 삭제: 저장된 파일 본문만 제거하고 `files.deleted_at`을 기록한다. 행(댓글·조회 포함)은 남겨 2주 관찰 지표가 사라지지 않게 한다. 삭제된 파일의 두 URL은 404다.
- 공유 링크: `/s/{token}` — 128비트 랜덤 토큰. 링크를 아는 사람은 보기+댓글 가능.
- `visitor_id`: APP_HOST의 익명 호스트 전용 쿠키(1년). 소유자 세션의 조회는 `views`에 기록하지 않는다. 소유자가 단 댓글·답글은 `is_owner=1`로 기록한다.
- 지표 SQL: (a) 소유자 외 `views`가 1건 이상인 파일 수 (b) `is_owner=0` 댓글이 1건 이상인 파일 수 (c) 파일 2개 이상(삭제 포함)을 올린 소유자 수. 소유자는 제공자별로 구분되므로 같은 사람의 다른 제공자 계정은 별도로 센다.
- 업로드 한도: 이미지 10MB, HTML 5MB(단일 파일). 기본값이며 사용하며 조정한다. 이미지는 매직바이트 검증, SVG는 제외.

**소유자 인증**
- Google·Microsoft·GitHub 개인 계정 OAuth(Auth.js). 도메인·테넌트 제한은 없다.
- 소유자는 `(provider, provider_account_id)`로 식별하고 email은 표시용이다. Microsoft 일반 테넌트의 email은 검증되지 않아 식별에 쓰지 않는다. 같은 사람이 다른 제공자로 로그인하면 별도 소유자가 된다(MVP 감수).
- Microsoft는 기본 issuer(`common`)를 쓴다.
- 사전 작업: 제공자별 OAuth 앱 등록 3개.

**검증 방식**
- 자동화 테스트 스위트는 만들지 않는다. 각 이슈는 수동 수용 기준으로 확인하고, 재현된 결함에 대해서만 테스트를 추가한다.
- 예외: HTML 격리는 적대적 HTML 샘플 1개로 "쿠키·localStorage 읽기, 부모 DOM 접근, 앱 API 호출 시도, 위조 `postMessage` 전송(범위 밖 값·긴 selector·HTML 문자열)"이 모두 앱 데이터에 닿지 못하고 검증에서 걸러짐을 한 번 확인한다.

### R2-1 — feasibility (minor)

**Problem**

> 업로드 HTML이 자체 `<meta http-equiv="Content-Security-Policy">`로 인라인 스크립트를 막으면 주입한 브리지가 실행되지 않아 핀 기능이 동작하지 않는다. 핀이 신뢰할 수 없는 페이지 DOM 안에 그려지므로 페이지 CSS(z-index, 전역 스타일)가 핀을 가리거나 바꿀 수 있다. 이번 변경에서도 다루지 않았다.

**Remedy**

> 브리지가 응답하지 않을 때의 사용자 표시(예: '이 파일은 핀 댓글을 지원하지 않음' 후 목록 댓글만 허용)를 정하고, 핀 요소 스타일 격리 방식(예: Shadow DOM)을 엔지니어링 리뷰 항목으로 남긴다.

### R2-2 — clarity (minor)

**Problem**

> `is_owner`가 추가됐지만 해결/재개를 누가 할 수 있는지(소유자만인지, 익명 작성자도 가능한지)와 답글도 해결 대상인지는 여전히 정해지지 않았다.

**Remedy**

> 해결/재개는 소유자 세션만, 최상위 댓글에만 가능하다(또는 다른 규칙)고 명시한다.

### R2-3 — clarity (minor)

**Problem**

> `comments.parent`로 답글을 표현하지만 답글 깊이(1단계인지 중첩인지)와 답글의 anchor 값(없음인지 부모 상속인지)이 정해지지 않았다.

**Remedy**

> 답글은 1단계, anchor는 null이라는 식으로 한 줄 명시한다.

### R2-4 — completeness (minor)

**Problem**

> 로그인 없이 누구나 댓글을 달 수 있는데, 소유자의 개별 댓글 삭제가 MVP 필수·제외 목록 어디에도 없고 author_name·body 길이 상한도 없다. 부적절한 댓글을 지우려면 파일 전체를 삭제해야 한다.

**Remedy**

> 소유자 댓글 삭제를 MVP에 넣을지 제외 목록에 넣을지 정하고, 입력 길이 상한을 업로드 한도 옆에 적는다.

### R2-5 — consistency (minor)

**Problem**

> Premise 2는 '인터랙션 보존이 실제로 필요한지는 이슈 #1의 관찰로 확인한다'고 하지만, The Assignment의 관찰은 '이미지 버전이 처음 동작하면' 이미지 링크를 보내는 것이라 HTML 인터랙션 필요성을 확인할 수 없다.

**Remedy**

> 관찰 대상 3명에게 인터랙티브 HTML 산출물을 공유받은 경험·필요가 있는지 묻는 항목을 이슈 #1에 추가하거나, Premise 2의 확인 방법을 다른 관찰로 바꾼다.

### R2-6 — feasibility (minor)

**Problem**

> 백업이 여전히 '/data 볼륨 스냅샷'이다. 실행 중인 SQLite(특히 WAL 모드)의 파일 스냅샷은 일관성이 보장되지 않는다.

**Remedy**

> `sqlite3 .backup`/`VACUUM INTO`로 백업 파일을 만든 뒤 스냅샷하거나, 스냅샷 시 컨테이너를 멈춘다고 적는다.

### R2-7 — feasibility (minor)

**Problem**

> HTML Content-Type을 `text/html; charset=utf-8`로 고정하면 EUC-KR 등 UTF-8이 아닌 HTML은 글자가 깨진다. 헤더가 문서 안 `<meta charset>`보다 우선한다.

**Remedy**

> 업로드 시 UTF-8만 받는다(검증 후 거부)고 명시하거나, 업로드 시 인코딩을 감지해 UTF-8로 변환한다고 적는다.

### R2-8 — feasibility (minor)

**Problem**

> 접근 A의 'CC ~3~4시간' 추정에 근거가 없다. 호스트 분기, 브리지 주입·postMessage 검증, HTML 선택자 앵커, OAuth `hd` 검증, 업로드 검증, 컨테이너 배포를 포함하면 낙관적이다. 접근 선택은 이 숫자에 의존하지 않는다.

**Remedy**

> 추정치를 빼거나 이슈 단위 추정으로 바꾼다.

### R2-9 — clarity (minor)

**Problem**

> 소유자 인증은 여전히 Google OAuth '가정'이고, 가정이 틀렸을 때의 대안과 이 확인을 언제(구현 전 어느 이슈) 끝내는지가 없다. 소유자 인증은 MVP 흐름에 필수다.

**Remedy**

> Open Question 1의 확인을 인증 구현 이슈 착수 전 선행 조건으로 두고, 불가 시 대안(예: 사내 SMTP 매직 링크)을 한 줄 적는다.

### R2-10 — completeness (minor)

**Problem**

> 호스트별 허용 경로와 호스트 전용 세션 쿠키는 추가됐지만, APP_HOST 앱 페이지 자체의 `frame-ancestors`/`X-Frame-Options`(앱 화면이 다른 페이지에 프레임으로 들어가는 것 차단)는 여전히 정해지지 않았다.

**Remedy**

> APP_HOST 응답에 `frame-ancestors 'none'`(또는 `X-Frame-Options: DENY`)을 둔다고 'HTML 안전 실행' 항목에 한 줄 추가한다.

### R2-11 — completeness (minor)

**Problem**

> 앵커 검증이 부모(브라우저) 쪽에만 정의돼 있다. 댓글 작성 API는 링크를 아는 누구나 직접 호출할 수 있으므로, 부모 검증을 거치지 않은 임의 anchor JSON(범위 밖 좌표, 긴 문자열, 문법이 틀린 selector, 알 수 없는 kind)이 저장될 수 있다. 문법이 틀린 selector는 브리지의 `querySelector`에서 예외를 던져, 처리하지 않으면 그 파일의 다른 핀 렌더링까지 멈출 수 있다. '위조된 앵커의 최악 결과는 엉뚱한 위치의 핀'이라는 주장은 이 경로까지 막을 때 성립한다.

**Remedy**

> 댓글 생성 Route Handler/Server Action에서도 같은 스키마(kind 허용 목록, 0~1 범위, selector 타입·길이 상한)를 검증한다고 적고, 브리지는 selector별로 예외를 잡아 해당 댓글만 '핀 없음'으로 처리한다고 명시한다.

### R2-12 — clarity (minor)

**Problem**

> 이미지도 `/c/{share_token}`에서 서빙하기로 했지만, 콘텐츠 응답 헤더 항목은 Content-Type을 `text/html; charset=utf-8`로 고정한다고만 적혀 있다. 이미지 응답의 Content-Type(매직바이트로 판정한 값인지)과 CSP sandbox 헤더를 이미지에도 붙이는지가 읽는 사람에 따라 달라진다.

**Remedy**

> HTML은 `text/html; charset=utf-8`, 이미지는 매직바이트 검증 결과의 `image/png|jpeg|webp`로 서빙하고 두 경우 모두 `nosniff`를 붙인다고 한 줄로 구분한다.

### R2-13 — clarity (minor)

**Problem**

> 외부 이미지·스크립트 로드를 허용하므로 `connect-src 'none'`은 외부 유출 차단 수단이 아니다. 업로드 HTML은 이미지 URL 쿼리 등으로 iframe 안에서 입력된 값이나 렌더된 핀 데이터를 외부로 보낼 수 있고, 익명 방문자의 IP·열람 시각을 제3자에게 알릴 수 있다. 앱 데이터는 불투명 출처로 보호되므로 안전 기준(성공 기준 2)은 유지되지만, 문서는 fetch/폼 차단이 무엇을 막는지와 이 남는 위험을 받아들인다는 점을 적지 않았다.

**Remedy**

> 기본 정책이 막는 것(앱 API 호출·폼 전송)과 막지 않는 것(외부 리소스 경유 유출·방문자 추적)을 한 줄로 적고, 업로더를 회사 도메인으로 제한하므로 MVP에서는 이를 감수한다고 명시한다.

### R2-14 — clarity (minor)

**Problem**

> 삭제 후에도 익명 작성자의 author_name·body 원문이 DB에 무기한 남는다. 지표 (a)(b)(c)는 행의 존재·`is_owner`만 필요하고 댓글 본문은 필요 없다. 소유자가 '삭제'를 눌렀을 때 댓글 원문이 남는다는 점과 보관 기간이 명시되지 않았다.

**Remedy**

> 삭제 시 댓글 본문·이름도 비울지(지표용 행만 유지), 원문을 남긴다면 사내 MVP 기간 한정 보관임을 한 줄로 정한다.

### R2-15 — completeness (minor)

**Problem**

> 소유자 제외가 로그인 세션 기준이라, 소유자가 로그아웃 상태·다른 브라우저로 자기 링크를 열거나 메신저 링크 미리보기 크롤러가 `/s/{token}`을 가져오면 '전달됨'(지표 a)으로 집계된다. 2주 소규모 관찰에서는 몇 건의 오집계도 판단을 바꿀 수 있다.

**Remedy**

> 알려진 오차로 받아들인다고 적거나, `views` 기록을 뷰어 페이지의 클라이언트 측 1회 호출(크롤러 제외)로 하고 소유자 로그인 시 해당 visitor_id의 기존 views를 제외하는 식의 최소 규칙을 정한다.
